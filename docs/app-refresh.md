# 刷新系统程序列表

这项能力调用受支持 9288 固件的原生程序扫描器，重新扫描 `A:\系统\程序\` 中的 EXE，并向原生桌面排队发送重绘消息。它用于上传或替换普通程序后更新系统记录、分类数量和文件位置缓存，无需为刷新程序列表而重启机器。

**更新 Debug 驻留服务本身仍需正常重启。** 已运行的旧服务不会因为其磁盘文件被替换而增加新命令；升级后运行新版 D88DEBUG，再连接电脑客户端。

## 使用

先在机端回到原生桌面，关闭弹窗和正在运行的应用，再点击电脑客户端的 **刷新程序列表**。成功回执包含刷新前后的总程序数和游戏分类数，表示原生扫描完成、桌面重绘已排队；它不保证屏幕在收到回执的同一时刻已经绘制完毕。

命令行可单独刷新：

```powershell
python -m host.client --port COM3 refresh-apps
```

图形客户端默认勾选 **程序上传后刷新列表**。只有直接上传到 `A:\系统\程序\` 的 `.exe` 文件完整提交成功、且设备声明支持刷新能力时，才提交一次独立刷新任务；普通文件不会触发。旧服务缺少能力位时，按钮禁用，程序上传仍可完成，界面会说明刷新被跳过。

命令行上传需要显式选择：

```powershell
python -m host.client --port COM3 file-put .\demo.exe 'A:\系统\程序\demo.exe' --refresh-apps
```

若文件上传已成功而后续刷新失败，上传结果保持成功，另行报告刷新错误。客户端不会因此回滚、重传文件或自动重放刷新；回到原生桌面后，可单独执行 `refresh-apps`。传输超时且结果未知时，应保留报告并重新连接后核对状态。

## 执行条件与失败行为

- 新服务通过 `CAP_APP_REFRESH`（bit 7）声明支持。旧版 `f9dc2295` 的 `caps=127` 不包含这一位；仅更新电脑客户端不能给旧服务增加能力。
- 扫描仅在调试器已拥有的 GUI1 桥接任务中执行，保留普通任务上下文、固件函数指纹和原生桌面检查。USB worker 不直接执行文件扫描器。
- 存在活动文件事务、其他未完成任务、应用窗口或弹窗时会拒绝刷新。设备状态不适合时，先回到桌面，再重新发起一次独立请求。
- 该命令仅调用已固定的原生扫描入口和桌面重绘路径，不接受函数地址或任意执行内容，不操作原始 NAND。
- 取消通过现有异步任务机制排队处理，不能在原生扫描调用中途强行打断。已经开始执行的任务可能先完成；收到完成结果后以实际结果为准。

## 协议

沿用 v1 帧头、序号和 CRC32。新增命令号 **21**，请求负载为空；它与文件命令共用单一异步 GUI 任务通道。

| 阶段 | 格式 |
| --- | --- |
| 提交 21 | 空请求，回复 `{job_id, result_signed}`，8 字节；拒绝时 job_id 为 0 |
| 查询 19 | 请求 `{job_id}`，回复 `{job_id,state,result_signed,length,data[length]}` |
| 取消 20 | 请求 `{job_id}`，只请求取消，不表示任务已经停止 |
| 成功 data | 6 个 LE u32：`{version=1,before_total,after_total,before_games,after_games,post_result=0}` |

`games` 指系统分类 8 的下载游戏数量。使用现有错误语义：参数无效 `-701`、忙 `-702`、执行/重绘错误 `-703`、固件检查失败 `-709`、取消 `-710`。不支持该能力的服务不会被当作支持服务调用。

## 既有验证与本次边界

历史调试确实使用过固件刷新能力，但当时由独立 **D88REF** 应用调用，尚未集成进 Debug 协议。D88REF 经正常 KF2 程序加载，在原生 GUI1 上调用扫描器并排队重绘；电脑调试器只负责文件传输、按键和只读核验。

保存的六轮成功真机记录均为 `no_restart=true`、扫描和重绘调用各一次、`post_result=0`、服务错误数 0。后续五轮观察到总程序数依次 `87→89→91→92→93→94`，游戏分类数 `13→15→17→18→19→20`；另有一次重复扫描保持数量不变。记录同时确认普通 GUI1 上下文、GP 为 0、固件指纹通过，桌面窗口与消息队列身份保持不变。

两个历史原生固件模型分别验证了普通 GUI1 入口调用和原生文件名加载路径，扫描后实际发现新上传的程序，且原有文件通道继续工作。模型 USB 寄存器由适配层模拟，不能作为物理 USB 证据。

上述记录证明原生扫描路径已使用过，**不能单独证明新增 Debug 命令、并发控制、自动刷新和新版驻留映像已完成真机验收**。本次构建与测试记录应单独绑定新的源码摘要、image_id 和设备载荷摘要，不沿用旧 `f9dc2295` 的整映像已验真机标记。

### 本轮原生固件模型

2026-11-07，新候选 `d276dce1` 对应的生产源码通过独立原生固件模型回归。模型经现有 GUI1 桥接和异步任务调用新增命令 21，使用真正的固件扫描器、文件系统与 ROS；USB 寄存器和请求入口由私有测试适配层模拟。

- 通过原生 PUT 创建一个系统类、一个游戏类的独立 KF2 测试文件，刷新前记录中均不存在，刷新后均被发现；总程序数 **76→78**，游戏分类数 **10→11**。
- 再次刷新计数保持不变，没有重复记录；原生桌面窗口与自有桥接 hook 保持不变。
- 存在活动 PUT 事务时，刷新返回 **BUSY (-702)**；该上传随后仍能完整提交，并通过 CRC 读回。
- 原有两轮带电启停、两次下载窗口覆盖后驻留继续运行、自动关机计数保活和停止报告原生回读也通过。

该模型使用单独复制并校验的 NAND 测试副本；原始私有种子文件前后 SHA-256 一致。普通 QEMU `-snapshot` 不保护本机模拟器自定义的 `nand-image` 文件属性，因此没有把原始镜像直接当作可写测试盘。

模型构建源码摘要为 `8291dbc71bb497e74c5abf5ef4d83bf8e263b8ccd368735c4f0f1dfa2e958ed2`，包含测试适配层，与发布映像的摘要分别记录。非 GUI/锁上下文及取消前后门禁由生产 C 模型精确验证；上述原生回归不等于新版物理 USB 或真机刷新验收。

### 本轮真机刷新验收

2026-11-07，新驻留服务 `image_id=d276dce1`、`caps=255` 在受支持的原版 9288 上完成刷新功能验收，原生桌面处于空闲状态，USB 线保持连接。

- 在现有 GET 事务仍然打开时，直接提交刷新命令返回 **BUSY (-702)**；清理该事务后，独立刷新正常完成，程序总数与游戏数保持不变。
- 备份已有的自有 `D88REF.exe`，以同一机端文件名上传一个类别改为游戏类的测试封装。测试封装也使用不同标题与自制图标，其执行载荷与备份完全相同，没有执行该测试程序。
- 使用实际 `upload_with_refresh` 路径完成替换和后续刷新：总程序数保持 **94**，游戏分类数 **20→21**，系统缓存中对应程序的分类字段 **9→8**。
- 再次独立刷新，游戏分类数保持 **21→21**，没有重复记录。
- 在清理步骤中恢复原始文件并再次刷新：游戏分类数 **21→20**，分类字段恢复 **8→9**。随后下载读回，文件 SHA-256 与备份完全一致，系统记录前 108 字节恢复一致；文件分配位置可以因重新上传而变化。
- 三次普通客户端重连均返回正确 image_id、`caps=255`、错误数 0。最终记录为 **500 次请求、0 错误**，快照缓冲已释放。

这次通过的检查针对真实缓存中的文件名、分类及文件位置记录，没有把程序标题当作该 112 字节缓存的字段。早先基于标题字段假设的探测未作为通过证据。

通过验收记录的 SHA-256 为 `6b2236115db962f7f66c62daf4ab915d59239e5880da79a9c5494a1f6b0d2310`；原始逐条系统记录和设备采集不随仓库分发。该次验收覆盖新增命令、上传后刷新、忙状态保护、恢复与普通重连，不代表所有固件或所有应用均兼容，也没有重新覆盖长期待机、STOP/原生磁盘恢复等独立项目。
