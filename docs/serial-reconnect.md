# 串口重连与单次取消修订

构建 `329f05d6` 在真机首次连接完成身份、状态和截图，但关闭后重新打开 COM3 的首个 PING 两次超时。显式等待 DTR 控制线稳定后，同一连接内的 20KiB 文件上传、下载、覆盖、取消和原生 GUI 左右键均通过；这是诊断连接，不能作为普通重连已修复的证据。

旧驱动在控制传输的 status ACK 后处理 DTR，并在该时刻清除 bulk RX FIFO。主机可能已经发送新 PING，软件随后清 FIFO 就会丢掉它。控制器模型精确复现了“硬件已 ACK 新 OUT，CPU 延迟 poll 后 RX 为零”；证据是本地 `build/usb-reconnect/race-before.json`。

修订版 `f9dc2295` 在 SET_CONTROL_LINE_STATE 的 SETUP 阶段先 NAK bulk、清旧数据并使旧会话失效。status ACK 后只提交 DTR、释放接收 NAK，不再丢弃新 OUT。已确认的旧控制传输还必须先于后来到达的 SETUP 生效；没有 ACK 的 SETUP 中断则只恢复原 DTR 的 gate，旧会话仍失效。重复 DTR1 或 RTS 变化同样形成协议会话边界，后续操作须先 PING；产品客户端没有添加睡眠或自动重放。

与此同时，文件任务发布单块完成结果时，会在短锁内保留原生文件调用等待期间收到的取消，继续调度同一任务直到清理结束。这避免一次 DTR/STOP 取消被单块成功结果吞掉。已完成的 PUT 提交可以返回成功，GET 最后关闭期间的取消仍返回取消；清理失败保留诊断。

四组控制器宏配置的模型与目标严格编译、232 项自动测试，以及捕获固件中的文件系统/GUI/ROS 回归已通过。重启激活后的真机验收也已通过：普通产品 Client 连续 5 次立即关闭/重开，第 6 次连接继续完成文件及截图按键测试，未增加 DTR 等待。20KiB 文件的新建、下载、替换、取消保持旧内容和同名保护均通过；LEFT/RIGHT 后画面完全恢复。最终 1294 次请求、0 错误，快照已释放。此结论不扩展为 16MiB、STOP/磁盘恢复或任意故障注入的物理验收。具体状态以 `dist/service-build.json`、`dist/validation.json` 为准。
